# glossary

이 프로젝트 안에서만 통하는 도메인 용어를 정의한다. **새로 합류한 사람(과 AI)이
코드를 읽기 전에 먼저 읽는 문서**다.

용어가 흔들리면 코드도 흔들린다. 같은 것을 어디서는 `order`, 어디서는 `purchase`,
어디서는 `transaction` 이라 부르기 시작하면 그때부터 대화도 코드도 어긋난다.

## 무엇을 적나

**일반적인 뜻과 이 프로젝트에서의 뜻이 다른 것**만 적는다.

| 적는다 | 적지 않는다 |
|---|---|
| 이 프로젝트에서만 특별한 뜻인 말 | 일반 기술 용어 (`캐시`, `마이그레이션`) |
| 업계 용어인데 우리가 좁게/넓게 쓰는 말 | 코드를 보면 바로 아는 것 |
| 비슷한데 구분해서 써야 하는 두 말 | 한 번 쓰고 마는 말 |
| 팀이 합의한 약어 | |

판단 기준 — **"이 말을 처음 듣는 사람이 코드에서 만나면 헷갈릴까?"**

## 형식

용어 표를 이 파일에 유지한다. 설명이 길어지는 용어만 따로 파일로 뺀다.

| 용어 | 정의 | 비고 |
|---|---|---|
| **ToolGroup** | 이 플러그인에서 기능을 묶는 단위. 새 기능은 기존 ToolGroup 에 넣을지 새로 만들지 먼저 정하고 시작한다 | 형제 저장소 `my-obsidian-tools` 가 같은 말을 쓴다. 기능을 옮길 때 어휘가 맞아야 번역이 필요 없다 |
| 데일리 노트 | 파일명에 `YYYY-MM-DD` 가 들어간 노트. 실제 Vault 는 `Work/Daily/2026-09/` 처럼 월별 폴더로 나눠 담는다 | Obsidian 코어 Daily Notes 플러그인과 무관하다 — 이 플러그인은 파일명만 본다 |
| 섹션 | `**[이름]**` 형태(볼드 대괄호)의 제목과 그 아래 본문. 다음 섹션 제목이나 `---` 를 만나면 끝난다 | **마크다운 heading 이 아니다.** 제목 줄 끝에 NBSP 가 붙은 실제 노트가 있어 정규화해서 비교한다 |
| 전일 진행 업무 / 금일 예정 업무 | 업무 양식의 두 섹션 이름. 어제 노트의 *금일 예정 업무* 가 오늘 노트의 *전일 진행 업무* 가 된다 | 설정에서 이름을 바꿀 수 있다. 코드에서 하드코딩하지 않는다 |
| 마커 / 영역 | `%% inno-scrum:start %%` ~ `%% inno-scrum:end %%` 처럼 한 쌍의 마커가 감싼 구간이 **영역**이다 | 마커 문자열은 설정으로 빼지 않는다 — 바꾸면 기존 노트의 영역이 전부 깨진다 |
| structural | 코드 블록·frontmatter **밖**이라 마커로 인정할 수 있는 줄인지를 가리키는 판정 (`markers.ts`) | 마크다운 예시 안에 적힌 마커를 마커로 오인하지 않으려고 둔다 |
| 스크럼(scrum) | 데일리 스크럼에 올릴 내용. 사용자 대상 문구는 **항상 `스크럼(scrum)` 으로 적는다** — 영어를 포함한다 | 커맨드 이름·안내 문구가 갈리지 않게 하려는 표기 규칙이다 |

## 규칙

- **코드의 이름과 일치시킨다.** 용어집에 `Draft` 라고 적었으면 코드에서도 `Draft` 다.
  적어놓고 코드에서 다르게 부르면 용어집이 거짓말이 된다.
- **이름을 바꾸면 용어집부터 고친다.** 코드만 바꾸고 두면 다음 사람이 낡은 정의를 믿는다.
- **혼동하기 쉬운 짝은 함께 적는다.** `Draft` 와 `Temp` 처럼 구분이 중요한 것은
  비고에 "무엇과 다른지" 를 쓴다. 정의만 있으면 경계가 안 보인다.
